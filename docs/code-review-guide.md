# Code Review 方法论（code-review skill 的 domain knowledge，v1.1）

本 skill 两种模式共用一套评审哲学：**评审的是"决策质量"，不是"代码行数"**。
PR 模式看 diff 里的决策，design 模式看文档里的决策。

## PR 模式

读 diff 的顺序：

1. **先看测试**：测试在测什么，决定了作者认为"对"是什么。测试缺失或只测 happy path，先记一笔。
2. **再看接口变化**：公开接口、配置项、数据格式的变更是 breaking 的高发区。
3. **最后看实现**：正确性 → 并发/边界 → 可读性。

必查清单：

- 安全：外部输入是否校验；secret 有没有进日志/报错；鉴权链路是否完整。
- 正确性：边界条件、空值、并发、时区/精度这类"看着没事"的坑。
- 可维护：命名是否说人话；注释解释"为什么"而不是"是什么"；删除的代码有没有留下僵尸引用。

红线：只读——永远不 comment、不 merge、不改代码。评审意见只进报告。

## Design 模式（无 pr_url 时自动进入）

评审对象是设计文档 / repo 脚手架，不是 diff。四个镜头（与 skill 输出的 rubric 对应）：

1. **自洽性**：目标 vs 机制有没有打架。每个设计目标反问一句"这个机制真的服务于这个目标吗"。重点盯三类：private/public 假设是否一致；"二期再做"的承诺与现实更新频率是否冲突；"黑盒交付"有没有藏起白盒。
2. **验收标准**：每个设计目标必须可证伪，配 Given/When/Then。"5 分钟上手""新人友好"这类目标没有验收标准就是空话。
3. **决策评审**：每个关键决策（D1..Dn）逐个给 keep / 修改 / 砍掉，并说理由。决策不是越多越好，互相打架的决策必须当场二选一。
4. **风险分级**：硬冲突（必须改，否则目标落空）/ 张力（有代价，给出最低成本的缓解）/ 可接受（记录，不 block）。不要把"张力"写成"硬冲突"吓唬人，也不要把"硬冲突"粉饰成"可接受"。

## 错误处理（v1.1）

- 没有 pr_url = 设计评审，不是失败：静默降级到 design 模式，run record 里记 `mode: design-review`。
- pr_url 格式错误、diff 拉取失败 = 真失败：抛错，fail-closed。陪审团不能评审它看不到的 PR。
