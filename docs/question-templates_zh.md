# 问题模板

> 为什么有这个文档：实战中，质量最大的杠杆不是 prompt 写得有多巧，
> 而是给评审团的信息给全了没有。一份四件套齐全的普通 prompt，
> 完胜信息单薄的"神 prompt"。偷原理，不抄咒语。

## 四件套

每个发给评审团的问题，都应该带齐这四部分：

1. **决策**——在定什么事（去 / 不去 / 改）？
2. **现状**——现在的事实是什么？
3. **约束**——硬限制：止损线、预算、立过的规矩、不能动的 deadline。
4. **时间线**——什么时候必须定，哪些 upcoming 事件框住了它。

四件套齐了，烂 prompt 也答得好；缺了，再强的模型也开始现编。

## 通用装配指令

每次运行由操作人追加（`thinktank.py` 尚未自动化），操作人不用记：

1. panel 先用自己的话复述问题，确认理解一致**再**回答。
2. 每条结论标注［查到的数据］还是［推断］。
3. 双 judge 分歧 → 如实呈现分歧点，绝不编造共识。

**隐私规则：** 先脱敏再提交。敏感信息一律用占位符；绝不粘贴
PII 或私密消息原文——panel 的 context 会发给外部模型。

## 模板

每套模板 = 四件套 checklist + 自动填充来源 + 输出结构 + 组装示例。
`[中括号]` 里的占位符由操作人在运行前填入真实数据。

### A. 下单前红队（深挖档）

用于任何难逆的操作：开新敞口、签字、发布。

- **输出结构：**
  1. 复述计划，确认理解。
  2. 这件事最可能亏钱 / 搞砸的三种方式。
  3. 计划本身的逻辑漏洞。
  4. 如果你是对手方，你怎么攻击它？
  5. verdict：去 / 改 / 不去，并点名最弱的一环。
- **组装示例：**"考虑在 [入场区间] 加 [数量] [标的]
（当前敞口 [X]；止损 [止损位]；催化剂：[事件]，[日期]）。
红队：找出这笔加仓最可能亏钱的三种情形。"

### B. 时间敏感信号深挖（深挖档）

触发器响了、要拍板时用。

- **自动填充：** 当日数据快照、定义触发器的计划文件、最新消息。
- **输出结构（六段）：** 背景 → 新鲜度 → 基本面（短/长）→
技术面（短/长）→ 处理 → 风险。
- **组装示例：**"信号：[标的] 收于 [价格]，触发器 [触发位]
（敞口 [X]；计划原文：[计划行]）。决策：执行 / 观望 / 改计划。"

### C. 定期复盘（快问档）

固定周期校准系统，不纠结单次决策。

- **输出结构：**
  1. 当前规则的 Top 3 漏洞。
  2. 哪条立过的规矩被违反 / 打折（附实例）。
  3. 具体的改规则建议，精确到触发数字。
  4. 下期盯什么。
- **组装示例：**"复盘 [日期] 当周：信号 [N] 条，命中率 [X%]，
执行偏差 [列表]。找规则漏洞。"

### D. 设计评审（快问 / 深挖看 stakes）

项目关键决策点用。

- **自动填充：** 相关设计文档、repo 现状。
- **输出结构：**
  1. 复述设计意图。
  2. 找茬：三个最可能出问题的地方。
  3. 有没有更简单的方案达到同样效果？
  4. verdict：过 / 改。
- **组装示例：**"决策：[项目] 的 [架构选择]
（背景：[D<n>]；约束：[列表]）。评审。"

### E. Offer / 职业决策（深挖档）

用于 offer 评估和谈判。

- **自动填充：** offer 条款（脱敏：去掉姓名和公司内部信息）；
当前 package；市场数据。
- **输出结构：**
  1. 拆 offer：base / bonus / equity 的真实价值。
  2. 对标市场。
  3. 谈判锚点和话术。
  4. 风险（title 降级、通勤、scope）。
  5. verdict。
- **组装示例：**"Offer：[公司类型] 的 [岗位]——base [X]、
bonus [Y]、equity [Z]（已脱敏）；现状 [CUR]；
回复 deadline [日期]。verdict：接 / 拒 / 谈，附锚点。"

### F. 操作人自查（深挖档）

定期找操作人自己的系统性偏差（比如净拣用户爱听的说）。

- **自动填充：** 本期报告和建议抽样、智囊团使用记录。
- **输出结构：**
  1. Top 3 系统性偏差，附实例。
2. 哪次该提醒没提醒，哪次是噪音。
3. 下期改进清单。
- **组装示例：**"抽查我 [周期] 的报告（抽样 [N] 份）：
找系统性偏差，附实例。"

## 三盆冷水

1. 智囊团是放大器，不是 oracle。分数看着不对，先怀疑外壳
（token 上限、prompt 格式、解析逻辑），再下模型结论。
2. 瓶颈通常是问题质量 + context 完整度，不是模型数量。
`--context-data` 注入比加模型更提分。
3. 预算花在高 stakes 和下单前评审上，不花在好奇心上。
